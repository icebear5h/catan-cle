# Qwen3.8-27B ASCII Variation Smoke

Date: 2026-08-16 (run completed 2026-08-17 UTC)

## Purpose

Test whether the earlier spatial-ASCII result survives a stricter benchmark and determine which capabilities fail independently of vision.

The prior 110-question run was not a topology benchmark: only tiles were arranged spatially, selected node/edge/robber cases were positive, count outputs were underspecified, and component-presence scoring could credit extra false entities. This smoke fixes those issues before comparing ASCII views.

## Controlled design

### Source boards

- 12 public board snapshots from 12 distinct replay games
- Density-stratified across opening, middle, and late states
- 12 distinct resource/number layouts
- Entity IDs deterministically permuted per board
- Tile, node, edge, and port IDs are opaque and cannot reuse the fixed numeric atlas

### Authoritative facts

Every prompt contains the same target-neutral `catan_full_public_graph/v1` facts:

- 19 tiles with cube coordinates, resources, numbers, robber state, corners, and sides
- 54 nodes with explicit occupancy and tile/edge/port incidence
- 72 edges with endpoints, adjacent tiles, and road ownership
- 9 ports with coordinates, directions, types, and attached nodes

No player summary, building count, road count, production answer, or target-specific fact is added. Every rendering parses back to one identical per-board digest.

### Six ASCII views

1. `flat_sorted` — concise sorted records
2. `flat_shuffled` — identical records globally shuffled
3. `sectioned` — records under entity headings
4. `tile_rows` — spatial tile rows plus full records
5. `local_blocks` — tile-local corner/side state plus full records
6. `topology_diagram` — node/edge/tile ASCII diagram plus full records

The last three add only derived/redundant views of canonical facts already present. They are semantically equivalent, but not token-length matched. Importantly, `tile_rows` and `topology_diagram` do **not** draw dynamic player buildings/roads into their spatial glyph layer; those occupations remain in the appended node/edge records. Only `local_blocks` repeats node and road occupation inline beside each tile.

### Questions

Exactly 60 questions, six per category:

- both inverses of six-way tile direction
- occupied/empty node state
- occupied/empty edge state
- connected/disconnected node pairs
- node-to-adjacent-tile exact sets
- occupied/empty port joins
- positive/empty nominal roll production
- separate settlement/city counts
- road exact sets plus counts

The evaluator supplies the six pointy-top cube deltas and nominal production rule equally to every format. There are no worked examples.

### Scoring and routing

- One strict JSON schema per task
- JSON duplicate keys rejected
- Exact keys, scalar types, tuple associations, and set membership required
- Extra keys, entities, duplicates, contradictions, prose, and broken tuples fail
- List order ignored semantically; canonical-string compliance tracked separately
- Qwen3.8-27B pinned to AkashML, fallbacks disabled
- Temperature 0, reasoning disabled, no image
- Responses admitted only when served model, provider, prompt hash, fact digest, scorer hash, and zero-reasoning checks pass

### Paired interpretation

Across the 60 questions:

- all six formats were correct on 35;
- at least one format was correct on 49;
- all six failed the same 11;
- only 14 questions varied by format.

Tile rows and the diagram each beat flat sorted on five paired questions and lost none, but the two-sided exact McNemar result is `p=0.0625`. Tile rows and the diagram split their own disagreements 3–3. No format difference reaches a defensible winner claim in this small, uncorrected multiple-comparison smoke.

Flat sorted and sectioned had identical correctness on every question. Headings alone did not help. Local blocks used 37% more prompt tokens than flat sorted without beating tile rows. Tile rows are therefore the most efficient provisional view among the tied leaders, not a proven best format.

## What Qwen is specifically failing at

### 1. End-to-end direction resolution in a long symbolic context

Across both inverse direction tasks, Qwen scored 28/72 (38.9%). Per direction:

| Direction | Direction → tile | Tile → direction |
| --- | ---: | ---: |
| LEFT | 5/6 | 1/6 |
| RIGHT | 2/6 | 2/6 |
| UP-LEFT | 3/6 | 5/6 |
| UP-RIGHT | **0/6** | **0/6** |
| DOWN-LEFT | 2/6 | 5/6 |
| DOWN-RIGHT | 3/6 | **0/6** |

The output confusions repeat across formats. For inverse questions, `UP-RIGHT` became `RIGHT` four times and `UP-LEFT` twice; `DOWN-RIGHT` became `DOWN-LEFT` five times. In the direct task, one `UP-RIGHT` target was wrong under all six formats, usually returning the same-row right neighbor.

This is an end-to-end failure, but the current task does **not** identify its internal stage. One answer requires locating both opaque IDs in a 6.5k–8.9k-token prompt, reading their coordinates or layout positions, subtracting cube coordinates, and mapping the delta through the supplied convention. The endpoint error cannot distinguish failed record lookup, coordinate extraction, subtraction, convention mapping, or diagram reading, and it does not prove that the model used a coarse spatial heuristic. A staged local probe is required before attributing a specific orientation-binding defect.

### 2. Multi-hop production grounding

Roll production scored only 3/36. All three exact answers were empty payout sets:

- positive production cases: **0/18 exact**
- empty production cases: **3/18 exact**

At tuple level, payout precision was 41.2% and recall was 58.3%. The model omitted valid recipients, added players/resources not adjacent to producing tiles, confused `BLUE` with `MYSTIC_BLUE`, and hallucinated production when no occupied corner should produce.

This task requires the full chain:

`roll → matching unblocked tiles → corner nodes → occupied building/color → settlement/city weight → aggregate color/resource`

None of the layouts solved that chain reliably. Local blocks did not materially repair it.

### 3. Filtering join results rather than retrieving them

Port occupancy scored 18/36, but the pattern is precise:

- every empty port was correct;
- every occupied port failed strict scoring;
- in all 18 occupied failures, the correct occupied tuple was present;
- the model also emitted the port's empty second node as an “occupant” with null color/building.

Thus Qwen found both attached nodes and the real building. It failed to filter an empty node out of an occupants-only result. The next prompt should explicitly say “omit empty nodes” to separate instruction interpretation from join ability.

### 4. Aggregation remains imperfect after output ambiguity is removed

Explicit JSON schemas fixed the prior scalar-output problem, but did not eliminate counting errors:

- building counts: 24/36 exact
  - color field: 36/36
  - settlement count: 27/36
  - city count: 30/36
- road inventory: 33/36 exact
  - color field: 36/36
  - edge set: 34/36
  - count: 33/36

One flat-sorted road response listed all six correct edges but reported count 5. Other misses omitted one edge and also undercounted. Building errors clustered on specific dense states rather than all formats uniformly.

### 5. Explicit record retrieval and simple topology are strong

The model was perfect on 144/144 calls covering:

- occupied and empty node state;
- occupied and empty edge state;
- connected versus disconnected node pairs;
- exact node-to-adjacent-tile sets of degree one, two, and three.

This shows reliable opaque-ID lookup, negative/default handling, exact set output, and simple one-hop graph queries. It does not show path planning or spatial reconstruction because those facts are explicit in the records.

## What this smoke still does not measure

- Coordinate rotations and reflections
- Node/edge screen-direction questions
- Paths, forks, cycles, blocking, or longest road
- Settlement legality and distance-rule composition
- Bank-supply-limited production
- Delta updates or cached-atlas formats
- Malformed/noisy input robustness
- Few-shot ICL versus instruction-only prompting
- Procedurally generated boards beyond the replay layouts
- Multiple trials per cell or model-serving nondeterminism
- Policy quality or strategic action selection

The sidecar formats are also not length matched. Tile rows, local blocks, and diagrams repeat facts already in canonical records, so any gain can be caused by redundancy or recency rather than geometry. Moreover, tile rows and the topology diagram spatialize static IDs/topology but not dynamic player occupation, allowing the model to ignore the visual layer and answer from appended records. A causal layout test needs dynamic node/edge occupation rendered directly into the diagram, a length-matched flat control, and diagram/row ablations.

## Recommended next diagnostic

Do not launch the 200-question × 3-repeat format ranking yet. First run a small capability ladder:

1. **Direction:** coordinate-only records versus rows versus diagram; rotate/reflection balance; direction rules at both prompt ends; zero-shot versus one worked example.
2. **Production:** separately score matching roll tiles, corner nodes, occupied corners, weighted payouts, and final aggregation.
3. **Port filtering:** explicitly require occupied nodes only.
4. **Counts:** require source ID lists and counts together, then score consistency.
5. **Layout causality:** compare spatial sidecars with equally long nonspatial duplicated-record controls.

If one view wins those focused paired probes, then promote it to a larger repeated planning benchmark.
